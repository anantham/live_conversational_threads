# Verified public wheels after bounded Docker download failures

Two Linux Docker pip runs timed out on unchanged upstream Zoom/OpenCV downloads. Stop that method. The approved recovery uses a different transport: fetch exactly the same two release wheels on the Mac with resumable HTTPS, compare size/SHA256 with official PyPI metadata, transfer public bytes only, and verify them again on Asus. No dependency/index/TLS/permission changes. Keep credentials/runtime outside every build context.

`prepare_verified_wheels_build.ps1` refuses source and artifact drift, unknown files/links, nested upstream output and existing destinations. It writes an external recipe that differs from upstream by exactly one pip RUN. BuildKit mounts only the two verified public files read-only and retains the existing public pip cache. Requirements remain byte-identical. Pass `--build-context lct_verified_wheels=<verified-directory>` with the generated Dockerfile and original clean upstream context. Verify native status and final image; no automatic retry.

Use separate `build-verified-wheels-*` receipts. The non-recording continuation accepts `-BuildMethod verified-wheels` and writes separate `runtime-verified-wheels-*` receipts, preserving the earlier failed readiness receipt. Its app/worker/port/identity/persistence/auth/S3 guards are unchanged. No worker or public route starts here. Wrong method is rejected by PowerShell ValidateSet. Actual constructor/parser/bytes, final image/imports and actual API/S3 are the acceptance evidence; preparation alone is insufficient.

Primary contracts: [pip find-links](https://pip.pypa.io/en/stable/cli/pip_install/#finding-packages), [PyPI release metadata](https://docs.pypi.org/api/json/). Payload inventory is exactly two public Linux CPython3.10-compatible upstream dependencies, not a different source release.

Native Windows full downloads worked, but a temporary Start-Process/WaitForExit/Refresh monitor returned null ExitCode after a successful process and prematurely stopped the second download. A harmless cmd exit0 reproduces null; the first wheel's official full hash and second wheel's exact80,113,664byte Mac-prefix hash prove the downloaded bytes. Do not equate HasExited/null with nonzero native status. `resume_verified_wheel.ps1` is the guarded one-time correction for that exact partial state: direct native cmd execution, immediate integer LASTEXITCODE plus0/37 controls, one resumable HTTPS request and final official full hash. It retains failed receipts and creates a separate ready context only on success. No automatic reuse on other partial states; inspect/falsify first.

## 18 October: decisive offline check and direct requirements

The approved single corrected diagnostic uses the actual upstream Python3/pip environment (the early cached layer lacks only the later python alias). Both exact verified Linux wheels are accepted and copied with network=none, --no-index and --no-deps; native exit0. These flags are diagnostic-only, not production dependency shortcuts.

prepare_verified_wheels_build.ps1 now accepts -BuildMethod direct-wheels. It names both verified files as explicit local pip requirements alongside the unchanged upstream requirements.txt, keeping all transitive dependencies, normal index/TLS and the public cache. The default verified-wheels recipe remains reproducible. Each prepared receipt records its method. start_direct_wheels_build.ps1 requires that exact method, diagnostic success and unchanged wheel/source/recipe hashes, and refuses a preexisting final image or completion/log holder. It performs one bounded build without automatic retry.

Use separate build-direct-wheels and runtime-direct-wheels receipts; prior failed/cancelled methods are preserved. The startup continuation accepts direct-wheels with otherwise unchanged identity, credential, persistence, authentication, API/S3 and cleanup guards. Neither build script starts a worker or public relay. Positive native final-image/API/S3 acceptance is still required.
