# Optional Google identity on the existing Sites Worker

Date: 2026-10-02. Status: selected by the human; implementation in progress. Actual OAuth registration, native account proof and real-data activation remain separate gates.

The human selected Google sign-in for private storage while keeping public guest entry, and explicitly approved `jose`. Use exact version 6.2.12 in the existing authentication-enabled custom Worker. Keep the native Sites ChatGPT identity and reserved sign-in/callback/sign-out routes intact. Google identity does not supply inference credits or Drive permissions.

Verify RS256 Google ID tokens with Google's fixed public JWKS endpoint, approved Web client audience, Google issuer, issuance/expiry and a server-signed short-lived nonce challenge. Login and logout writes require the exact request origin and an explicit same-origin custom header. Credential bodies have byte and time bounds; tokens are not logged, published, or retained in browser storage. Public runtime config exposes only readiness and the configured public client ID. Google remains inactive unless the enabled flag, client ID, signing secret and D1 binding are present.

Mint a one-hour HttpOnly, Secure, SameSite=Strict host cookie, signed with `jose`, and require its matching unrevoked D1 session on every private request. Keep only hashed random session/challenge IDs, Google subject, creation/expiry and revocation timestamps; no profile email, Google access token or recording is stored in this session table. Expired sessions are removed on the next accepted login. A challenge cannot be replayed, including after logout. Preview metadata is bounded to 256 sessions per Site and five per subject, including revoked receipts until expiry; these are safeguards, not production scale approval. A storage outage or invalid/revoked/ambiguous Google cookie fails closed instead of silently using another ChatGPT identity.

The stable private owner is the pair `(provider, subject)`. The additive generated migration gives every existing file the `chatgpt` provider without changing its owner, immutable blob key or contents. New Google files use `google`; list, read, upload quotas, finalization, recovery, compensation and deletion require both fields. Do not auto-link identities by matching email. Global capacity/fence accounting stays shared and approved keep-until-deletion retention is unchanged. Authenticated Soniox admission resolves the same identity; provider configuration and funding stay inactive.

The UI obtains config at runtime, loads Google's official Identity Services script only after a deliberate action, uses the signed nonce and posts the returned credential to this Worker. Success reloads the page to clear prior account UI. Logout revokes the app session before top-level native Sites sign-out clears any preexisting ChatGPT identity. Show stage, elapsed time, unknown remaining time, cancellation, timeout and retry; retain small payload-free timing history. Public browsing stays usable. Synthetic fixtures do not prove native cookies or real Google accounts.

Finite checks: valid and refused signatures/claims; nonce/CSRF/replay; timeout/cancellation/retry; expiration/revocation/ambiguous cookies and DB failure; two synthetic Google subjects plus an identical legacy ChatGPT subject across private effects/quotas/recovery; additive migration; guest and disabled-provider behavior; actual two-Google-account hosted proof before personal uploads. Obtain eligible non-OpenAI independent review of the coherent source/test/config/migration diff before publication. Native Google configuration and real accounts remain required for complete journey acceptance.

Assumptions: Sites dispatch protects its trusted ChatGPT header; the native Worker honors secure app cookies, D1 transactions and registered HTTPS origins. Confidence: 0.8 before native Google proof. Prediction: verified accounts use their own synthetic private storage; other accounts/forged credentials cannot. Fallback: retain public entry, existing identity and synthetic-only storage while Google is inactive; do not activate personal data or paid providers to bypass a failed check.

Alternatives considered: defer Google, leaving the selected private identity journey unfinished; add a separate authentication service, expanding deployment/configuration beyond this slice. Keep the selected standard verifier in the existing Worker. No new service, Google API scopes, spending, private disclosure or domain cutover follows from the library approval.

## 2026-10-02 privacy disclosure and activation amendment

The public Sites preview needs a guest-readable `/privacy` page and a visible link beside optional sign-in before Google sign-in is made public. The optional access panel is omitted on that route so it neither obscures the policy nor starts a session check there; returning Home restores it. The disclosure must track the implemented data paths: Google Identity Services is loaded after deliberate action; the ID token is verified and not retained; the D1 session row keeps Google subject, hashes of random session/challenge IDs and timestamps; the cookie lasts one hour and expired rows are removed on a later accepted login. Native ChatGPT identity is separate. Browser-local files do not upload themselves. Private D1 metadata and R2 file bytes are retained until owner deletion; this preview currently accepts only fixed synthetic private uploads. Whole-file public publication is a separate explicit action, and public downloads cannot be recalled. The page names operator and infrastructure access, the two bounded payload-free browser timing histories, and an operator contact. Its wording is scoped to this Sites preview, not the legacy local/Tailscale app, and must be reviewed before publication.

After review and human authorization for activation, keep the existing synthetic-private and public-publication feature flags plus DB/BUCKET bindings. Configure only `LCT_GOOGLE_CLIENT_ID` (public Web client ID), secret-marked `LCT_GOOGLE_SESSION_SECRET` (32–512 characters), and `LCT_GOOGLE_AUTH_ENABLED=true`, then redeploy the reviewed Site/source to apply the runtime environment. A configuration review may name these variables but must exclude actual IDs, project/account inventory and secrets. Native hosted two-account checks and explicit real-data activation remain separate acceptance gates; this amendment itself authorizes neither deployment nor personal uploads.
