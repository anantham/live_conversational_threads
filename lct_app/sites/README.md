# Sites Worker compatibility slice

Run `npm run build:sites-worker` from lct_app to create dist/server/index.js.
The bundle exposes the Cloudflare Worker fetch interface using Web APIs only.
The normal `npm run build` and Vercel default handlers remain available.

Implemented endpoints:

- POST /api/proxy/chat: forwards a visitor's own API key and streams the response.
- POST /api/proxy/realtime-token: preserves the existing ephemeral-token request.
- OPTIONS for these endpoints: preserves the existing request guards, and accepts the exact Site request origin.

The adapter uses Cloudflare's ingress client-IP header for the existing approximate per-isolate limit. API replies are not cacheable. It never reads an owner trial key, persists request data, or logs credentials/payloads. BYOK audio-file transcription remains browser-to-OpenAI.

Frontend requests need an ASSETS binding. The adapter reports full-backend endpoints as unavailable; it does not impersonate the Python health endpoint. The original Worker-only slice was not deployable by itself. The complete public journey still needs live-microphone integration and saved-graph navigation before switching the public domain; the parallel checkpoint below adds its separate build and Site identity.

No new packages, database, storage bucket, credentials, public access, or paid inference are configured here. See ../../docs/plans/2026-10-01-lct-sites-migration.md for the delivery sequence and ../tests/intent/sites-serverless-worker.md for validation intent.

## Parallel Site build and identity checkpoint

`npm run build:sites` builds the React frontend into `dist/client` and the Worker into `dist/server/index.js`. The dedicated frontend config reads no environment files or ambient VITE variables, copies no public directory, and adds only the existing favicon. Both output directories are checked before publication. This prevents unrelated public experiments/ciphertexts and owner configuration from entering the artifact. Existing local/Vercel builds are preserved.

`node sites/export-source.mjs ABSOLUTE_EMPTY_DIRECTORY` exports a bounded technical source tree for the standalone Sites source repository. It excludes Git history, environment files, operational documents, tests/fixtures and unrelated static artifacts; symlinks and nonempty destinations are rejected. Initialize the retained template using the Sites project setup helper, then register once and persist the returned project ID. The canonical identity is in `../.openai/hosting.json`; reuse it on continuation.

`GET /api/auth/session` reports the dispatch-provided Site-specific user ID with `no-store`, or returns401 and the dispatch-owned sign-in path when identity is absent. It returns no email or service credential. A service access token cannot replace user identity. This app relies on Sites dispatch to validate identity and strip spoofed caller identity headers; local header fixtures do not prove that deployment boundary. Actual signed-in access must be verified before claiming native sign-in complete.

Browser HTML navigation to an unrecognized asset path falls back to the app shell for React Router deep links, including a managed-asset redirect to the same-origin canonical root. Auth, external and query redirects retain their response; missing asset files and unsupported backend API routes preserve errors. Sites dispatch owns sign-in, sign-out and callback routes; no app-owned OAuth implementation is added.

The user selected public access for this parallel preview. The Sites build defines its own literal mode flag: Home and browser-local browsing load without a backend health probe, key prompt or login. An optional session panel uses the actual Worker response contract; sign-in/sign-out use top-level dispatch links. Session checking never blocks public content, records at most eight payload-free timing samples, shows elapsed time with unknown remaining time, and supports timeout/retry/cancellation. It neither displays nor persists the user ID.

Public cloud sharing and private cloud storage remain unimplemented; opening a browser-local file does not publish it. Future public saves must label visibility explicitly, while every private storage route must authorize the trusted signed-in owner server-side. Live recording, Soniox and cloud graph reads still require subsequent roadmap stages; do not change the public custom domain or enable owner-funded traffic from this artifact alone.

Sites Browse mounts only its browser-local library at this checkpoint. It does not mount the legacy owner audio/server-history sections or request their records. Those sections remain available in the original local/Vercel builds.

## Prepared OpenRouter generation — 2026-10-03

GET /api/cloud/openrouter/status separates configuration/schema readiness from current admission availability. POST /api/cloud/openrouter/generate requires exact Site Origin, application/json, x-lct-openrouter-consent: generate-v1 and a source object accepted by createRecordingTranscript. It returns request_id and a validated artifact; it never saves or publishes source/results. No model, credential or limit submitted by the browser controls the provider request.

No runtime default enables this route. Activation requires explicit LCT_OPENROUTER_ENABLED=true, LCT_OPENROUTER_PROJECT_BUDGET_CONFIRMED=true, server-only OPENROUTER_API_KEY, LCT_OPENROUTER_MODEL, LCT_OPENROUTER_PROVIDER, LCT_OPENROUTER_DATA_COLLECTION (allow/deny), LCT_OPENROUTER_AUDIENCE (public/authenticated), LCT_OPENROUTER_MAX_REQUESTS (1..200), LCT_OPENROUTER_MAX_OUTPUT_TOKENS (1..8192), DB and generated migration0006. Optional LCT_OPENROUTER_LONG_MAX_OUTPUT_TOKENS (up to 16384, never below the live cap) applies to transcripts longer than 5 minutes (imports, replay); the Worker decides from the validated transcript's span, and storing it needs migration 0019. Deploy order: disable generation (`LCT_OPENROUTER_ENABLED`/`LCT_GEMINI_ENABLED` false) and confirm no unresolved attempts, apply D1 migration 0019 (a table rebuild that copies every row), re-enable, then set the long cap. Until 0019 is applied, long admissions return 503 `schema_unavailable` and short ones still work. Do not enable until the exact model/provider/data policy and dedicated non-resetting key allowance are approved and verified. Request/token caps alone are not a dollar ceiling.

Only random IDs/times/token caps/confirmed completion times are retained in lct_openrouter_attempts. Lifetime counts persist; at most2 unresolved attempts and10seconds between admissions. Unknown failures retain their slots; there is no automatic retry/refund/reset. Input arrival is bounded to30seconds/512KiB, provider completion to90seconds/2MiB (60 seconds until 2026-11-03); the browser waits up to125seconds in total. Error bodies exclude raw provider details and keys. Delivered abort signals propagate and clean up readers; native client-disconnect delivery needs Cloudflare enable_request_signal and remains a later hosted check. This prepared source has not activated paid traffic or changed the current Site.


## Selectable Gemini and OpenRouter generation

The recording page selects `/api/cloud/gemini` or `/api/cloud/openrouter`, with independent recipient-specific consent. Gemini uses Google AI Studio's Gemini Developer API OpenAI-compatible endpoint with `GEMINI_API_KEY`, explicit `LCT_GEMINI_MODEL`, `LCT_GEMINI_ENABLED=true` and `LCT_GEMINI_PROJECT_BUDGET_CONFIRMED=true`. The current launch uses `gemini-3.5-flash-lite`; configure an eligible model for the key's project. This is not the Vertex AI endpoint, and key creation alone does not establish Cloud credit eligibility.

OpenRouter prefers `OPENROUTER_API_KEY_2` when present; otherwise it retains `OPENROUTER_API_KEY` for existing deployments. It never retries through the other key or service. Both backends share the existing `lct_openrouter_attempts` ledger and `LCT_OPENROUTER_AUDIENCE`, `LCT_OPENROUTER_MAX_REQUESTS`, and `LCT_OPENROUTER_MAX_OUTPUT_TOKENS` limits. No migration or quota reset accompanies adding Gemini. Status is configuration/admission readiness, not proof of provider authentication or billing coverage. Request caps are not a currency cap.

Google sign-in is separate: `LCT_GOOGLE_CLIENT_ID` is a public Web OAuth client ID with this Site origin authorized; `LCT_GOOGLE_SESSION_SECRET` is a random server-only signing secret; `LCT_GOOGLE_AUTH_ENABLED=true` enables the reviewed identity flow. No Google client secret or Gemini key belongs in frontend configuration. `LCT_PRIVATE_STORAGE_ENABLED=true` permits deliberate owner-scoped uploads within the existing storage limits. Activation requires owner authority and actual hosted identity/provider acceptance; synthetic fixtures alone cannot establish that acceptance.

## Approved model fallback — 2026-11-03

`LCT_OPENROUTER_FALLBACK_MODELS` is optional. It holds up to three comma-separated OpenRouter model ids that the owner has approved. When the primary `LCT_OPENROUTER_MODEL` has no route, they are tried in order. Unset or empty means no fallback, and behaviour is unchanged. A malformed list (bad id, more than three, duplicate, the primary repeated, empty entry) leaves OpenRouter generation unconfigured; it never runs with a shorter list.

Each attempt is a complete request with the same `provider.only: [LCT_OPENROUTER_PROVIDER]` and `data_collection`; only `model` changes. OpenRouter's own `models` fallback array is deliberately not used, because its documentation does not say provider preferences bind every listed model. The next model is tried only on HTTP 404 or 503, where no provider accepted the request. 400–403, 429, 502 and every 200 response, valid or not, end the attempt. One admitted generation is still one ledger row. The response names the model that served, and status reports `fallback_models` so the consent screen lists every model that may receive the transcript. Every fallback is logged as `model_fallback` with upstream status and positions only.

`GET /api/cloud/health/openrouter` also reads `/api/v1/models/{model}/endpoints` for each approved model and reports `model_routes` (`approved`, `available`, `unknown`). A model counts as available when an endpoint tag equals the provider slug or starts with `provider/`. A delisted model (404) counts as missing; other unreadable listings count as unknown. With zero available and zero unknown, `reachable` is false, so the Site shows "Needs attention" before any transcription. Gemini (Google AI Studio) and the private replay path stay single-model. Replay's price ceiling is computed from the primary model only.

Choose fallbacks whose price, output format, provider and speed you have checked: a fallback can cost more per request than the primary, and every attempt shares the route's single generation window (90 seconds; it was 60 until 2026-11-03). On 2026-11-03 `google/gemini-3.6-flash` did not finish a 20-minute transcript inside the old 60-second window, while `google/gemini-3.5-flash-lite` finished a 5-minute one in 7 seconds.

### Map structure (2026-11-04)

- **Long turns split before generation.** A map chunk links whole utterances, so `createRecordingTranscript` now starts a new same-speaker utterance after the first sentence end once a turn reaches 60 s or 150 words, or at any token boundary at twice either bound. The decision uses only tokens already seen, so periodic maps of a live session keep earlier ids. Saved `.threads` files keep their embedded utterances.
- **The prompt asks for structure:** one coherent moment per chunk (backchannels folded in), single children only where a tier adds meaning, a parent's evidence covering its children, and digressions as their own node.
- **`evidence_mismatch` is always logged, never enforced.** It fires when a child cites utterances its parent's evidence lacks, with counts by tier only. Node ids summarise the conversation, so they stay out of logs. It is logged whatever `LCT_OPENROUTER_DEBUG` says, and the map is still saved.
- **`node scripts/score-map-structure.mjs <map.threads>...`** prints the same structural counts for saved maps. They are counts, not a quality score.
- Measured effect and limits: `docs/reviews/2026-11-03-long-input-envelope.md`, section "Map structure A/B".

### Generated reference repair

Strict JSON-schema output cannot make a reference point at a node the model actually declared. On 2026-11-03 a 20-minute reply declared `node-idea-intro` and referenced `idea-intro` throughout. Before validation, `repairGeneratedReferences` (`src/services/cloud/generationReferenceRepair.js`) resolves dangling typed references (parents, secondary parents, edge endpoints, thread moments) only when the reply shows one systematic drift. ONE operation must fix all of them: add or strip one delimiter-ended prefix (`node-`) or one delimiter-led suffix (`-node`). Each dangling reference must have exactly one candidate at its own level. Every declared id at a touched level must carry the added affix (or none may carry the stripped one). Within each reference family (parents, edge endpoints, thread steps), the references to any one level must be wholly resolved or wholly dangling, so a lone dangling reference among resolved ones is never re-pointed. The observed reply drifted only at chunk→idea, so that one level was wholly dangling while topic/theme/arc parents resolved. Beside references that already resolve, nothing may be stripped, and the added affix must read as a convention in one of two ways: every resolved reference carries it (the 3 November reply, prefixed at every tier), or it is a prefix confined to one tier of a reply whose ids lead with their tier. That second case requires all of the following: one tier is touched; that tier declares at least two ids, each the affix plus its tier word, a delimiter and a name containing a letter or digit (`node-idea-programming`), which makes every dangling id tier-named too; every resolved reference at another tier names its tier the same way; and the affix does not begin with a tier word (`idea-`, `topic1-`, `ideas-`). So the prefix lands before the tier word, never on the name. On 2026-11-04 a reply declared only its ideas as `node-idea-programming`, referenced them as `idea-programming`, and named every other tier the same way (`chunk-01`, `topic-intro`). Refused: a shared word on bare names (`non-water` against `water`); a suffix on the name (`idea-water` → `idea-water-shortage`); a prefix before a trailing tier word (`non-water-idea`); a tier-word affix (`idea-`, `topic-`, `topic1-`, `ideas-`); `ideas-…` ids; a bare `idea-` or `idea--`; a declared sibling at the tier that doesn't name it (`node-shade`); a lone node at the tier (`counter-arc-garden`); drift at two tiers; and a bare resolved id elsewhere. Any malformed reference slot disables the repair. Neither a dangling id nor its repaired target may be declared at another level, no declaration may repeat, and a purely numeric affix (`-2`) never counts. Only ids the validator itself would accept (non-empty, trimmed, at most 158 characters) take part. References that already resolve are never changed. Anything else is left untouched and rejected exactly as before, and the full validator still runs after a repair. Every repair is logged as `reference_repair` (operation, affix, count, no content) whatever `LCT_OPENROUTER_DEBUG` says, and returned as `reference_repair` in the map and replay responses. It is not yet stored in the saved `.threads` file. Remaining risk: a reply in which every node and every resolved reference begins with the same word (e.g. `no-`) is indistinguishable from a structural prefix like `node-`, so a family of references omitting it would be repaired. Likewise, at a single tier, a shared word placed before tier-named ids (`non-idea-x` against `idea-x`) is indistinguishable from `node-`. The repair log is how the owner would see that.
